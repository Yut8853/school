# AIブログ編集・公開ルール

## 1. 目的と実行範囲

スクール「0→1」の読者が、ホームページ制作の具体的な課題を一つ解決できる記事を作る。検索向けの水増しや同じ記事の言い換えを量産しない。

「ブログを作って」で毎回1本。AIが企画・調査・執筆・表紙制作・検証・コミット・プッシュまで担当する。これは依頼されたときに実行する運用であり、定時の無人投稿や外部AI APIへの自動課金は行わない。テーマ指定があればランダム選定を省略する。

## 2. 最初に読むもの

- `AGENTS.md`、`BLOG.md`、このファイル
- `content/blog/*.md` の全記事のタイトル・概要・主見出し
- 直近5記事の本文、テーマに近い既存記事の本文
- `data/blog-topics.json`（候補テーマ）
- 記事でスクールに言及する場合は該当するカリキュラム・受講料・規約・講師ページ
- `git status --short`、ブランチ名、origin、リモートとの差分

## 3. ランダムな企画選び

`npm run blog:idea` は未使用テーマから候補を最大3つ抽選する。記事数の少ないカテゴリを選ばれやすくし、直近2本と同じカテゴリは重みを下げる。候補はテーマだけでなく、読者・記事の型・解決する問い・実践課題を含む。

1. 候補を既存記事と比較し、「同じ悩み・同じ結論・同じ手順」になるものを除外する。タイトルだけ違う記事は禁止。
2. 原則として最初の適切な候補を採用。近い記事がある場合は対象・原因・完成物が異なると説明できるときだけ採用する。
3. テーマの小ささを守る。「HTML完全解説」より「見出しの順序を直す」のように一つの問いに絞る。
4. 直近記事と導入、章立て、具体例が同じにならないようにする。乱数は構成のきっかけであり、事実や技術の正しさをランダムにしない。
5. 候補が尽きたら新しい問題を最低10件追加し、重複を確認してから再抽選。使用済みIDをリセットしない。
6. ユーザー指定テーマもtopicIdを付け、同じ問いの重複時は既存記事の改善を優先する。変更の希望が不明なら重複しない切り口で新規作成。

抽選結果は標準出力のJSONで確認する。`--seed=任意の文字列`で再現可能。seed未指定は暗号学的乱数を使用する。候補抽選は原稿や公開状態を書き換えない。

## 4. 読者・テーマ・記事の型

読者は記事ごとに一つに絞る：完全未経験／HTML・CSSを少し書ける／一つのサイトを公開したい／制作工程を見直したい。

カテゴリ：学習ガイド、HTML / CSS、JavaScript、アクセシビリティ、デザイン、公開・運用、制作の進め方。

型：手順解説、失敗の直し方、判断基準の比較、小さな制作課題、確認チェックリスト、制作過程の解説。単なる語句の定義だけで終えない。比較は結論を煽らず使い分けを示す。

毎回、具体例はテーマに合った架空の案件から選ぶ（地域のお店、個人の作品紹介、イベント、教室、企業案内など）。同じパン屋の例ばかり続けない。架空・模擬の例であることを本文に明記する。実案件・受講者実績を創作しない。

## 5. 調査と根拠

- 技術仕様、ブラウザ対応、ライブラリAPI、料金、制度、時点で変わる情報は最新の一次資料を開いて確認する。検索結果の抜粋だけで確定しない。
- 技術はMDN、W3C/WAI、WHATWG、ブラウザ・ツールの公式ドキュメントを優先。
- 参照元はfrontmatterのsourcesにURL・確認日・何を裏付けるかを記録し、該当する本文に通常のMarkdownリンクを置く。読んでいない資料を参考文献として載せない。
- 学習の進め方など、編集上の提案だけの記事はsourcesを空にできる。その場合も技術的な断定や実証されていない効果を混ぜない。
- 引用は短く必要な範囲だけ。参考記事の文章や構成を翻訳・言い換えで複製しない。
- 未検証の数値、受賞、売上、学習効果、合格率、利用者の声は書かない。スクールの条件や保証を独自に増やさない。
- 医療・投資・法的判断や不正利用を主題にしない。Web制作の課題に戻す。

## 6. 執筆

目安は本文1,200〜2,400文字。コードとURLを除く自動検査は900〜3,600文字を許容する。長さのための水増しはしない。

- タイトル：具体的な困りごとと得られる理解を示し、おおむね20〜48文字。誇張や「完全」「絶対」「最強」を使わない。
- description：一覧で独立して意味が通る50〜140文字。
- 冒頭：読者の困りごと、この記事で扱う範囲、読後にできることを短く示す。「現代において」「いかがでしたか」は使わない。
- h2は3〜7個。本文にh1を置かない。見出しだけ読んでも作業の流れが分かるようにする。
- 説明→具体例→読者が確かめる方法を含める。失敗例は必ず修正例・修正理由とセットにする。
- 用語は初出で短く説明。英語と日本語を無意味に重ねず、読み手の知識を前提にしすぎない。
- 「力を育てる」「可能性を広げる」「世界に挑む」「守り続ける」等の抽象的な結びを避け、実際の操作・判断を書く。
- 同じ文末の連続、同じ内容の導入と結論、「〜まで」の重複、不要な箇条書きを読み直す。
- 最後に10〜20分程度で取り組める小さな課題または具体的な確認手順を一つ設ける。実測していない作業時間は目安として扱う。
- 関連する既存記事への文脈に沿ったリンクを1つ以上、無料レッスンまたはカリキュラム等へのリンクを1つ設ける。営業目的のCTAは1つまで。料金訴求を毎段落に入れない。
- 著者は「0→1 編集部」。講師が執筆・検証したという表現を、本人の確認なしで付けない。

## 7. コード例・画像

- コードは目的に必要な最小構成。省略箇所と、単体では動かない例を明記。
- HTMLは意味に合う要素、フォームのlabel、buttonのtype、画像のalt、キーボード操作を確認。
- CSSはスマートフォン、横幅のはみ出し、focus-visible、prefers-reduced-motionを必要に応じて扱う。
- JSはエラー処理、イベントの後始末、ユーザー入力の扱いを確認。シークレットや認証情報を埋め込まない。
- 実行できるコードは実行して確認。ブラウザー操作を行えないときは、その事実を公開前レビュー記録に残し「確認済み」と書かない。
- 表紙は記事slugと一致する独自SVGを用意する。既存の白地・黒文字・オレンジと補助色、図解中心の雰囲気に合わせる。960×600、タイトルを小さな画像に詰め込まない。外部ロゴや無断利用画像を入れない。
- 本文で図を使うなら意味のあるalt／説明を付ける。一覧の装飾表紙はalt空でよい。

## 8. 原稿メタデータとレビュー記録

新規原稿は `_template.md` を使い `editorialVersion: 1`、`topicId`、`audience`、`format`、`primaryQuestion`、`outcome`、`sources` を必須とする。公開日は実際の日本時間の日付。下書きはdraft:true。新記事でfeaturedを勝手に入れ替えない。

`content/blog/reviews/slug.json` に次を記録する：
- `slug`、`reviewedOn`（日本時間の日付）
- `topicReason`：選んだ理由と既存記事との差
- `factCheck`：実際に確認した根拠と留保
- `codeCheck`：実行した検査、またはコードなし
- `visualCheck`：実際に確認した画面幅・結果、または未実施の理由
- `limitations`：残る制約の配列（なければ空）

これはAIが作業事実を記録するためのもの。自動テストがレビューの正しさを保証するわけではない。原稿とレビュー記録に個人情報や秘密情報を入れない。

## 9. 検証とプッシュ

1. `npm run blog:lint`で必須項目・文字数・見出し・topicId重複・出典リンク・表紙・レビュー記録を検査。既存6本だけは初期記事として扱う。新記事を初期記事リストへ追加して検査を回避しない。
2. 内容を読み直し、上記ルールで編集。自動検査の成功だけで品質確認を済ませない。
3. `npm run build && npm run test:blog && npm run check`、`git diff --check`。
4. 利用可能なブラウザーで一覧、カテゴリ、検索0件、記事、目次、関連リンク、コードコピー、PC／スマートフォン表示を確認。利用不可の場合は未実施を明記し、既存の静的検査とコードテストを実行して先に進める。
5. `git fetch origin`後に履歴を確認。共有ブランチの履歴は書き換えない。リモートが先行していたらユーザーの変更を保持して取り込み、影響する検証を再実行。
6. 原稿・レビュー・表紙・生成されたブログHTML/CSS・RSS・サイトマップ・必要な設定のみをステージ。`git add .`は使わず、差分とステージ済みファイルを確認する。
7. 内容が分かるメッセージでコミット（例：`blog: explain accessible form labels`）、`git push origin HEAD`。
8. リモートの対象ブランチのSHAとローカルHEADの一致を確認。プッシュまで失敗なく終えてから完了報告する。
9. 最終報告は記事名、テーマ選定の要点、検証結果、コミット、プッシュ先、残る確認だけ。デプロイ未確認ならその旨を書く。

プッシュ権限・認証が不足する場合は実装と検証を終えてから、具体的なエラーと必要な対応を伝える。「あとでプッシュできます」という提案だけで終了しない。
